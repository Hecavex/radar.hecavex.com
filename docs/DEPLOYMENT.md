# Deployment

This is the HECAVEX maintainer runbook for the production service at [radar.hecavex.com](https://radar.hecavex.com), not a general self-hosting guide. The service is published through GitHub Pages. Scheduled workflows maintain generated archives and public snapshots on a dedicated data branch. Deployment executes trusted source and imports only validated data blobs.

## Source and data cutover

The checked-in migration uses protected source `main` and data-only `radar-data`. This section is an activation runbook, not a statement that the owner has completed the cutover or enabled settings. Do not disable collectors, shorten their windows or grant a blanket Actions source-protection bypass.

After the migration PR is merged, the owner initializes the data branch from the **exact final merge SHA**, using that revision's trusted helper. The helper must preserve generated data arriving before the merge, not a stale rehearsal seed. The owner separately applies source PR/check protection and verifies the first real data write, fresh-source snapshot and exact live release. A missing data branch fails closed until initialization. Rehearsals belong in disposable repositories and cannot substitute for production verification.

The owner-only bootstrap interface is:

```sh
python -m hecavex_radar.data_branch bootstrap --repository . --source-revision EXACT_MERGE_SHA --branch radar-data --push
```

Use a trusted source checkout for every reader and writer. Never check out the data branch as the execution workspace. The common read interface is:

```sh
python -m hecavex_radar.data_branch materialize --repository . --branch radar-data --view operational --state-file /path/outside-checkout/radar-data-base.json
```

Replace the state path with a writable private temporary path. `publication` selects the last snapshot marker commit instead of the latest operational head. Actions additionally supplies `--github-output` and consumes `source_revision`, `data_revision` and `publication_source_revision`. Source CI uses the separate `materialize-fixture` command for a pinned coherent fixture. It does not create publishable state and its derived quality artifacts are ephemeral.

The seven writers call `publish` with their validated state file and one fixed writer identity: `certstream`, `ct-search`, `urlscan`, `brand-assets`, `domain-context`, `passive-context` or `snapshot`. The helper restricts changed paths by writer, verifies source has not moved and compares the selected data head before updating it. Publication makes at most four compare-and-swap attempts. CertStream can carry its completed window across changes disjoint from `data/certstream/` and `public/data/collection-health.json`, preserving newer unrelated blobs and the publication marker. Other computed writers refuse intervening generated input/output changes. A conflicting data write or changed source requires a fresh bounded workflow run, not an unrestricted rebase or replacement of unobserved data.

`radar-data-manifest.json` identifies source, base data revision, writer, timestamp and the bounded file inventory. Only snapshot sync advances `radar-publication.json`, identifying its source and input data revision. Collectors preserve that marker. These branch-root metadata files are not themselves claims that a deployment is live.

## Pages

The repository's Pages source must be **GitHub Actions**. [`.github/workflows/deploy-pages.yml`](../.github/workflows/deploy-pages.yml) verifies the frontend and builds the overview, retained signal pages, stable brand pages, `/changes/`, `/history/`, `/brands/`, `/trends/`, `/associations/`, `/tools/`, `/dataset/`, `/methodology/`, `/docs/`, the non-sending `/reporting/` utility, and the localized `/lt/` routes into `dist/`. It deploys after successful source CI when matching publication data exists, after a successful snapshot sync, or after a finalized CertStream failure committed changed public collection health. Routine collector-state commits wait for the next hourly snapshot instead of rebuilding the complete site four times per hour. A candidate-producing collector attempt requests an immediate bounded snapshot sync, while a collector failure remains eligible for an immediate verified health deployment. Every deployment path runs the same frontend checks. The triggering source must equal current protected `main`, and the selected data publication marker must identify that same source. Pages imports the operational view to retain the latest collector failure health, verifies the data trigger is an ancestor of the selected data revision, and rechecks both remote heads before deployment. Successful hourly synchronization normally advances the public success heartbeat and therefore creates a deployment even when the signal set is unchanged; archive-only URLScan, CT-search, and context-state commits also wait for that snapshot sync.

[`sync-radar.yml`](../.github/workflows/sync-radar.yml) validates the configured inputs each hour. Every successful run advances `lastSuccessfulSyncAt` in the live snapshot, even when the observations are unchanged; `generatedAt` advances only for a material data or source-state change. The same validated signal list is projected into the observation and reviewed STIX files. The synchronized release also includes history, optional signal details and context changes, aggregate health/change/relation views, the bounded global event record, Atom/RSS/JSON Feed projections, deterministic per-brand feeds and their directory, daily coverage-aware trends, public review-quality metrics, a reviewed-only MISP manifest/event projection, the independent official-domain warning list, schemas, checksums, and the manifest. The workflow separately refreshes the deterministic brand-coverage ledger and balanced review queue from the same exact materialized inputs. Persisting that set in one data-branch Git commit keeps the static distributions aligned. Each regular file is first replaced through a temporary file; the Git commit is the atomic repository publication boundary. Live-snapshot retention and sharp-drop protection compare against the actual previous publication rather than an artifact-only copy. The Pages job has no collector credentials and never changes data.

The deploy freshness gate includes the STIX path so a STIX-only correction cannot be mistaken for an unchanged snapshot. The production artifact gate requires both STIX distributions. The static verifier checks the observation Bundle's 2 MiB cap, structure, raw-domain safety boundary, and exact correspondence to `radar.json`; publication validation applies the standard STIX 2.1 validator to both Bundles. The reviewed Bundle may contain an Identity only when no exported confirmation exists. Otherwise it contains time-bounded Indicators and a linked Sighting for each Indicator that has a matching current or retained public observation summary. Both files are ordinary static JSON downloads, not TAXII endpoints, and need no credential or repository variable.

The publisher compares new output with rows seen during the previous 30 days and refuses an unexpected sharp reduction. Older rows no longer block a legitimate empty snapshot. For a deliberate reset of recent data, manually dispatch **Sync radar snapshot** with **Allow this run to bypass the snapshot-size guard** enabled. The override applies only to that manual run. The independently replaced `collection-health.json` is intentionally outside the hourly release manifest and checksum set; its synchronized aggregate is `pipeline-health.json`.

## Automation

### Capacity and recovery checks

`python -m hecavex_radar.capacity` reports current byte headroom, row counts, retention and partition limits without making network requests. CI records this inventory. `pnpm verify:growth` creates a separate disposable fixture tree and builds both languages with 5,000 retained records under the existing 256 MiB deployment and per-response gates. Synthetic fixtures never enter public source data or a deployment.

URLScan checkpoints are compact-serialized under the same 256 KiB cap. Before requesting another bounded page, the store reserves space for the update. Under pressure it compacts optional replay-ID hints and then evicts only completed query caches. Pending continuation cursors never expire or get evicted to make space. A full set of pending slots refuses new queries with `state-capacity`, rather than calling the provider and losing the checkpoint. Capacity is preflighted before archive publication, and checkpoints commit only after archives, preserving safe at-least-once replay on a failed final write.

Indexed CT records `deferred-backoff` when no request is performed. It keeps the last actual request, last success, next allowed request time and actual consecutive failures separate, including in EN/LT collection health. An elapsed cooldown is not a promised workflow start time. Fair rotation preserves failed query cursors and does not increase request budgets or ignore rate limits.

After rollout, confirm a real URLScan hunt completes and clears the failure streak without falsely completing its backlog. Observe actual CertStream gaps for 48 hours. Neither local regression tests nor a corrected relay guarantee GitHub scheduler availability or continuous listening coverage.

Cron schedules use UTC. Each CertStream run samples one eight-minute window at an intended four-per-hour cadence; even if all 96 daily runs start and complete, this is at most 768 minutes, or 53.3% of a day, not continuous collection. Native slots at 08, 23, 38, and 53 minutes remain the backstop. Every finalized collector emits the fixed `certstream_writer_completed` repository event through its existing contents-scoped token. The payload contains only the fixed workflow name, job outcome, run ID, `main` ref, the writer's validated starting revision, and one controlled collection outcome. A separate completion relay uses the `radar-certstream-cadence` environment's six-minute wait timer, cancels an older pending relay, checks the fixed collector workflow for newer queued or running work, and dispatches exactly one replacement run. Relay invocations retain distinct `cadence-relay` provenance. At worker start, both automated trigger paths compare the persisted latest-attempt start with the declared 15-minute interval. An invocation up to five minutes early waits only until the due boundary, re-reads the persisted state, and starts only if another queued worker did not claim it; an earlier invocation is skipped. Manual maintainer runs bypass the cadence guard. The guard therefore absorbs scheduler jitter without admitting starts less than 15 minutes apart or exceeding the documented 96-window daily ceiling. A skipped invocation emits the same bounded completion handoff. The six-minute protected-environment wait and due-time guard still apply, and there is no runner sleep loop. Completed no-op runs are not treated as owners of a future relay. A non-success workflow completion provides a fallback handoff for cancellation or a failure before the notifier. A second completion relay checks the fixed snapshot workflow after each successful collection. Routine outcomes dispatch only when no sync is active and the latest successful sync is at least 45 minutes old. `healthy-matches` bypasses the age test; if a sync is already in progress, the relay queues one follow-up unless another sync is already waiting, preventing an older checkout from delaying a newly accepted candidate. Routine collector-only CI completions do not trigger a full Pages rebuild. Snapshot writers emit the distinct `snapshot_writer_completed` event, while a failed collector completion may publish its bounded health state immediately. Both relays have Actions write and contents read only; neither can modify repository data directly. The hourly `crt.sh` job uses the same serialized CT-writer group, so it cannot update the shared archive while a live listener is finalizing. A failed CT provider request trips a run-scoped circuit, persists a bounded exponential or `Retry-After`-directed `nextAttemptAt`, and prevents the remaining query allowance from being spent into the same outage. URLScan, DNS/RDAP context, and snapshot writers use the shared archive-writer group. Scheduled and manual writer code is pinned to `main`, while generated writes target only `radar-data` through the narrow publisher. All writers refuse a changed source. Only the bounded CertStream disjoint-data merge described above tolerates a changed data head. Snapshot output is recomputed in a fresh run rather than rebased over changed inputs. Existing workflow concurrency and bounded retry limits remain in force. Source protection must not require a blanket Actions bypass for these data-only writes.

The live publication verifier waits at least 30 minutes before judging a repository snapshot missing from Pages. It then validates the deployed feed manifest against the snapshot success timestamp, digest, and byte length. When the checked-in and deployed synchronization timestamps are identical, it also requires the deployed Radar artifact digest and length to match the checked-in manifest. One immediate cache-busted retry is allowed only for a manifest/snapshot pair that appears transitional; a persistent mismatch fails. An absolute three-hour successful-sync age limit applies even when repository and live data are equally old. The verifier also checks the stable English, Lithuanian, trends, methodology, and custom-404 routes for their expected language and canonical boundaries. Every Pages deployment emits `/.well-known/hecavex-release.json` with `revision` and `sourceRevision` equal to the trusted source SHA and `dataRevision` equal to the selected exact data SHA. The verifier checks that built revision pair, so an old but reachable site cannot pass the release check. A failure updates one issue carrying the `radar-live-health` label and a later healthy run closes that same issue. The verifier reports deployment state only; it cannot change data or redeploy the site.

The repository environment `radar-certstream-cadence` must retain a six-minute wait timer and no required reviewers. The workflow's branch and upstream-event checks are the dispatch boundary; the environment supplies only the runner-free delay. Removing the timer makes the relay start another eight-minute sample immediately after each completion and changes the documented sampling cadence.

Python 3.12 automation installs reviewed, SHA-256-locked dependency sets from [`requirements/`](../requirements/). Scheduled writers use the minimal runtime lock; CI uses the development-tool superset. The checked-out package is then installed without resolving additional dependencies or creating an unconstrained build environment.

Frontend verification also enforces deterministic first-party gzip and total-output budgets documented in [`PERFORMANCE.md`](PERFORMANCE.md). The check uses built files only and has no network-performance dependency.

## Weekly dataset releases

The weekly publisher is deliberately separate from hourly snapshot synchronization. The normal path and explicit `data_sha` use the validated data-branch publication view. An explicit `source_sha` retains the legacy historical-main data-only extraction path. These selectors are distinct and cannot supply executable tooling. An explicit `data_sha` must identify a coherent snapshot publication commit, not an intermediate collector commit. For compatibility, the weekly manifest names the selected data SHA `sourceCommit` (or the historical main snapshot SHA on the legacy path) and names the current trusted main SHA `toolingCommit`. These weekly field names are distinct from the Pages release document. It executes only the triggering current-`main` release tooling. A historical backfill is read as bounded regular data blobs below `public/data/` and `data/history/context/` in a separate temporary root; code, Actions, scripts, and dependency files from that commit are never checked out or executed. Current schemas and validators then validate that selected publication before packaging it, excluding only `collection-health.json` because that latest-attempt document advances outside the atomic snapshot. URLScan-derived context rows are eligible only when `URLSCAN_DERIVED_REDISTRIBUTION_CONFIRMED` is exactly `true`; otherwise release validation excludes them. The archive is reproducible byte-for-byte from the same data and tooling commits; its standalone manifest records both commits and the SHA-256 digest of every packaged dataset and context file, while the identical in-archive manifest is necessarily outside its own inventory. A deterministic SPDX 2.3 document inventories the current trusted-tooling Python runtime and pnpm dependency graph. A published release is evidence of a successful weekly run only when GitHub reports the release as immutable and its attestations verify.

HECAVEX must first enable **Release immutability** in the repository's **Settings > Releases** section, then set the `RADAR_IMMUTABLE_RELEASES_CONFIRMED` repository variable to `true`. The workflow intentionally fails before creating a draft while that confirmation is absent. It never changes the setting itself. GitHub recommends attaching every asset to a draft before publication; the workflow follows that sequence and verifies the published release's `immutable` API field. See [`DATASET-RELEASES.md`](DATASET-RELEASES.md) for release and recovery semantics.

The CertStream job initializes health before installing collector dependencies, lets setup and collection failures reach a finalizer, and stages the daily archive and health document in one commit. A failed or no-input attempt is therefore recorded before the job reports failure. Every successful window appends one bounded aggregate row to its Vilnius-day `attempts.ndjson`; zero matches still produce that dated partition, while `domains.ndjson` appears only when candidates exist. Routine health measurements are published with the next hourly snapshot, candidate-producing runs request an immediate snapshot, and committed failures remain eligible for an immediate health deployment. Hard runner cancellation, platform outage before checkout, or an exhausted push retry cannot be recorded by a workflow that no longer has execution or write access. The latest-health document replaces one fixed path and is capped at 32 KiB; daily attempt rows contain no raw certificate names or candidates.

The checkpointed CT-search job rotates through six reviewed brand queries by default. It asks `crt.sh` for indexed JSON results, considers at most 500 rows per query, and limits a query's first run to a seven-day bootstrap. A default 50-row/1,000-ID overlap replays bounded prior results for late provider indexing. A query with unprocessed new rows keeps its partial checkpoint for its next turn. Rotation advances past queries actually attempted, including failures, while an archive-cap failure never advances that query's result checkpoint. The job stages state and accepted shared CT archive rows before a final step propagates polling or publication failure. The state is capped at 128 KiB and contains no unpublished certificate name or candidate domain. Its cursors make only those keyword searches resumable; they do not represent CT-log tree positions or complete global CT coverage.

The URLScan job treats the hunter and state publication as separate steps. The commit step always stages `data/urlscan/`, including state written before a hunter failure, and a final step then propagates a hunt or publication failure to the workflow result. An absent secret is not a failure: the hunter performs no request, records `configured: false` and `skipped-not-configured` on the first material transition, and exits successfully. Later identical unconfigured runs remain visible in Actions history, but timestamp-only differences are ignored so they do not create empty state commits. Runner cancellation, an outage before checkout, or a rejected push has the same unavoidable observability limit described above.

Each URLScan provider query also persists one hash-only `search_after` checkpoint in `data/urlscan/search-checkpoints.json`. Query completion is based on the provider total, returned page length, and cursor progress rather than the provider's 10,000-result `has_more` signal. Budget exhaustion, rate limiting, or an unavailable request leaves the checkpoint partial and cannot clear or advance it. Only aggregate complete/partial/backlog counts and the oldest backlog progress time reach public pipeline health; query terms are never written to the checkpoint file.

The DNS/RDAP job rotates through 20 current published candidates by default. It issues only A, AAAA, CNAME, NS, and MX questions to Cloudflare DNS-over-HTTPS and registration lookups for the registrable parent through the IANA-selected RDAP service; it never requests a candidate webpage. Its atomic state contains defanged answers, the defanged queried registration scope, and limited registrar/lifecycle/status fields, drops records that leave the snapshot or age beyond 14 days by default, and is capped at 2,500 rows and 4 MiB. The job commits its latest `completed`, `partial`, `failed`, or `empty` outcome before propagating a failed result. The next hourly synchronization can place current context in optional signal detail sidecars and its aggregate state in pipeline health.

| `HECAVEX_FEED_TOKEN` | Secret | Optional with HECAVEX | Read-only bearer token for the HECAVEX endpoint. |
| `PHISHDESTROY_SEED_ENABLED`, `CERTPL_SEED_ENABLED` | Variables | Optional | Set either to `false` to disable that transient URLScan seed adapter. Seeds never publish directly or appear as source labels. |
| `RADAR_HISTORY_DETAIL_DAYS` | Variable | Optional | Detailed daily history retention, 30 days by default and bounded from 7 to 90. |
| `RADAR_HISTORY_SUMMARY_DAYS` | Variable | Optional | Compacted history retention, 730 days by default and bounded from 30 to 3,650. |
| `RADAR_HISTORY_MAX_SIGNALS` | Variable | Optional | Public history row cap, 5,000 by default and bounded from 1 to 25,000. |

The private false-positive review ledger is not a deployment input and must remain outside the repository. An operator may deliberately export its sanitized active decisions to `data/review/public-decisions.json`; synchronization rejects malformed, oversized, future-dated, duplicate, or cross-brand decisions. See [`REVIEW-WORKFLOW.md`](REVIEW-WORKFLOW.md).

The sanitized proposal workflow is a separate pre-decision path. Before using it, repository **Actions > General** settings must allow GitHub Actions to create pull requests. The workflow restricts dispatch to maintain/admin collaborators, validates controlled defanged fields, creates a new proposal branch, and opens a draft pull request. It does not consume issue prose, create an assessment, or change `public-decisions.json`. CODEOWNERS documents the intended reviewer, but repository rules must separately require CI and approval on `main`; deletion, non-fast-forward, and linear-history protections alone do not enforce review.

The current repository state must not be interpreted as external acceptance: URLScan-derived temporal redistribution stays disabled until permission is confirmed, the reviewed MISP feed stays disabled until a current MISP importer and same-UUID tombstone propagation pass, and precision remains unavailable until an actual public analyst-review sample exists.

Public screenshot URLs must be hosted on exactly `urlscan.io`, regardless of which source supplied the observation. Tuning limits, lookback windows, and other bounded defaults are documented in [`.env.example`](../.env.example) and the relevant [workflow files](../.github/workflows/).

The URLScan guards remain below the provider's published fixed-window quotas. The checked-in counters measure only successful responses observed by the hunter and are not a substitute for URLScan account usage. HTTP 429 stops further requests safely. Search queries are limited to the rolling previous seven days; each two-hour run attempts all currently bounded candidates, with cursor resumption if a lowered cap or budget interrupts the set. Radar calls only the public search and result endpoints, never scan submission or a candidate site.

Scheduled and manual URLScan dispatches share the same persisted UTC-day counters. A default scheduled run can issue at most 25 searches and 100 result retrievals, below the provider's 120-per-minute limits; the twelve scheduled runs total at most 300 and 1,200 respectively before lower practical query counts, below both the local daily guards and provider daily quotas. The two-hour schedule places no more than one scheduled run in an hour. Manual dispatches are serialized by the archive-writer concurrency group and consume the same daily budget; operators must not use manual dispatch as a way to burst provider windows.

Before HECAVEX enables or changes URLScan collection on the live service, operators must review the current [URLScan Terms of Service](https://urlscan.io/terms/) and obtain any permission required for the intended display or redistribution of report metadata and screenshots. An API key proves authentication, not redistribution permission.

## Custom domain

[`public/CNAME`](../public/CNAME) declares `radar.hecavex.com`. The Pages custom domain must match it, with this DNS record:

```text
Type: CNAME
Name: radar
Target: hecavex.github.io
```

Verify `hecavex.com` in the owning GitHub account or organization and retain GitHub's `_github-pages-challenge-*` TXT record. This protects the custom domain if repository or Pages configuration changes. Enable HTTPS after GitHub completes its DNS and certificate checks.
